## Overview

Monitor standard DMTF Redfish resources exposed by a baseboard management controller (BMC).

The collector covers endpoint health, systems, chassis, managers, processors, memory, storage, drives, volumes,
network adapters and ports, PCIe, power, cooling, environmental sensors, batteries, leak detection, firmware,
assemblies, and LogService state. It publishes:

- per-component metrics and state charts;
- complete one-level rollups with population/completeness, min/average/max, fixed histograms, and state counts;
- deterministic ComputerSystem virtual nodes when `node_mode: system_vnodes` is selected;
- current hardware inventory through `redfish:inventory`;
- retained LogService records through `redfish:logs` when a referenced `redfish_logs` backend is ready.


The collector authenticates to the Redfish ServiceRoot over HTTP or HTTPS, traverses only its closed standard-resource
registry, and follows same-origin links. It prefers session authentication in `auto` mode and falls back to HTTP Basic
authentication when the endpoint does not support a usable session. Requests are bounded by the configured timeout,
retry count, and concurrency.

Collection is best-effort: one unreadable resource does not stop independently reachable resources. Missing current
values produce gaps rather than zeroes. Complete membership scans obsolete removed components; partial scans retain
prior membership evidence without replaying stale readings.


This collector is supported on all platforms.

This collector supports collecting metrics from multiple instances of this integration, including remote instances.

A read-only Redfish account is normally required. No local elevated privileges are needed. Log storage requires the
Netdata log directory to be writable by the Agent through a configured `redfish_logs` job.


Redfish can be monitored further using the following other integrations:

- [Redfish log backend](/src/go/plugin/go.d/collector/redfish_logs/integrations/redfish_log_backend.md)

### Default Behavior

#### Auto-Detection

No endpoint is auto-detected by the collector itself. Configure static jobs, DynCfg jobs, or enable the independent
Redfish Service Discovery pipeline under `go.d/sd/redfish.conf`.


#### Limits

Detailed component charts are admitted atomically per logical owner and component family. The default cap is 100
components per family; exceeding it suppresses that whole detail group while preserving inventory and complete
one-level rollups. Set `charts.max_detailed_components_per_family: 0` for no configurable cap.

LogService admission is atomic across the selected services and defaults to 256 services. Protocol response bounds,
closed traversal registries, and request concurrency protect the Agent from malformed or hostile payloads.


#### Performance Impact

The default interval is 60 seconds. BMCs are often slow and may serialize requests internally. The collector starts
conservatively with three concurrent requests and uses the configured ceiling unless the ServiceRoot explicitly
prohibits multiple HTTP requests, in which case it uses one. It does not probe or automatically change the job's
cadence. The complete endpoint walk is also bounded by the configured `update_every`; when it cannot finish, the
collector publishes independently completed data as partial and rotates unfinished member work across later cycles.
Use a larger `update_every`, narrower `collect` pattern, or lower concurrency if the BMC becomes overloaded.

### Prerequisites

#### Enable and authorize Redfish

Enable the BMC's Redfish service and create a least-privilege monitoring account that can read the desired systems,
chassis, managers, sensors, storage, and LogService entries.


#### Establish network and TLS trust

Ensure the Netdata Agent can reach the BMC. Prefer HTTPS with a trusted BMC certificate or configure `tls_ca`.
`tls_skip_verify` is available for legacy/self-signed deployments but permits machine-in-the-middle attacks.


#### Configure a log backend if logs are required

Redfish metrics do not require log storage. To ingest LogService entries, configure and enable a `redfish_logs` job.
Omitted endpoint routing selects the backend job named `default`; an explicit missing backend never falls back.

#### via UI

Configure the **redfish** collector from the Netdata web interface:

1. Go to **Nodes**.
2. Select the node **where you want the redfish data-collection job to run** and click the :gear: (**Configure this node**). That node will run the data collection.
3. The **Collectors → Jobs** view opens by default.
4. In the Search box, type _redfish_ (or scroll the list) to locate the **redfish** collector.
5. Click the **+** next to the **redfish** collector to add a new job.
6. Fill in the job fields, then click **Test** to verify the configuration and **Submit** to save.
    - **Test** runs the job with the provided settings and shows whether data can be collected.
    - If it fails, an error message appears with details (for example, connection refused, timeout, or command execution errors), so you can adjust and retest.


#### via File

The configuration file name for this integration is `go.d/redfish.conf`.

The file format is YAML. Generally, the structure is:

```yaml
update_every: 1
autodetection_retry: 0
jobs:
  - name: some_name1
  - name: some_name2
```
You can edit the configuration file using the [`edit-config`](https://github.com/netdata/netdata/blob/master/docs/netdata-agent/configuration/README.md#edit-configuration-files) script from the
Netdata [config directory](https://github.com/netdata/netdata/blob/master/docs/netdata-agent/configuration/README.md#locate-your-config-directory).

```bash
cd /etc/netdata 2>/dev/null || cd /opt/netdata/etc/netdata
sudo ./edit-config go.d/redfish.conf
```

##### Examples

###### Central out-of-band monitoring with vnodes

Create one deterministic Netdata vnode for each ComputerSystem exposed by the BMC.

<details open><summary>Config</summary>

```yaml
jobs:
  - name: bmc
    url: https://192.0.2.1/redfish/v1/
    node_mode: system_vnodes
    username: monitoring
    password: ${file:/etc/netdata/redfish-password}
    tls_ca: /etc/netdata/redfish-ca.pem

```
</details>

###### In-band collection without duplicate nodes

Publish the local server's BMC metrics on the existing Netdata node.

<details open><summary>Config</summary>

```yaml
jobs:
  - name: local-bmc
    url: https://192.0.2.1/redfish/v1/
    node_mode: local
    system_uri: /redfish/v1/Systems/1
    username: monitoring
    password: ${file:/etc/netdata/redfish-password}

```
</details>

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.

The closed executable registry emits standard Redfish contexts only when the endpoint exposes their source properties.
The `redfish.*` namespace covers endpoint operations, resources, readings, and one-level rollups. Common hardware readings
reuse `system.hw.sensor.*` contexts with `_collect_module=redfish`.



### Per endpoint

Per Redfish endpoint job collection and log-routing state.

Labels:

| Label      | Description     |
|:-----------|:----------------|
| endpoint_job | Redfish job name. |
| endpoint_key | Stable canonical endpoint key. |

Metrics:

| Metric | Description | Dimensions | Unit |
|:------|:------------|:----------|:----|
| redfish.collection.status | Overall endpoint collection result. | success, partial, unavailable | state |
| redfish.collection.duration | Endpoint collection-cycle duration. | duration | seconds |
| redfish.collection.http_requests | HTTP request attempts, retries, and redirects in the cycle. | started, retried, redirected | requests/cycle |
| redfish.collection.resources | Resource discovery and acquisition population. | discovered, readable, unreadable, unknown | resources |
| redfish.collection.logs_route | Selected log backend route state. | disabled, ready, unavailable | state |


### Per resource or reading

Per-component standard resource and normalized-reading charts, optionally attributed to generated ComputerSystem vnodes.

Labels:

| Label      | Description     |
|:-----------|:----------------|
| resource_kind | Normalized Redfish resource kind. |
| resource_name | Current resource display name. |
| logical_owner_name | Proven logical owner name. |
| component_family | Cardinality and rollup component family. |

Metrics:

| Metric | Description | Dimensions | Unit |
|:------|:------------|:----------|:----|
| redfish.system.health | ComputerSystem health state. | ok, warning, critical, unknown | state |


### Per one-level rollup

Complete child population aggregated only to its immediate approved rollup owner. The metrics below document the
invariant and representative rollup shapes; additional `redfish.aggregate.*` summaries, fixed histograms, and state
counts appear when the endpoint exposes their source capabilities.


Labels:

| Label      | Description     |
|:-----------|:----------------|
| rollup_owner_kind | Immediate rollup owner resource kind. |
| rollup_owner_name | Current rollup owner display name. |
| component_family | Aggregated component family. |

Metrics:

| Metric | Description | Dimensions | Unit |
|:------|:------------|:----------|:----|
| redfish.aggregate.population | Child population and acquisition coverage. | total, readable, unreadable, unknown, histogram_eligible, histogram_ineligible | components |
| redfish.aggregate.completeness | Collection and histogram completeness state. | complete, incomplete, histogram_available, histogram_unavailable | state |
| redfish.aggregate.acquisition_state | Child counts by acquisition state. | readable, unreadable, unknown | components |
| redfish.aggregate.temperature | Minimum, average, and maximum temperature across the immediate child population. | minimum, average, maximum | Celsius |
| redfish.aggregate.temperature_distribution | Fixed temperature histogram across the immediate child population. | lt_40, 40_50, 50_60, 60_70, 70_80, 80_85, 85_90, 90_95, 95_100, ge_100 | components |
| redfish.aggregate.health | Child counts by normalized health state. | ok, warning, critical, unknown | components |
| redfish.aggregate.reading_alarm | Child reading counts by normalized alarm state. | clear, warning, cap, alarm, critical, emergency, fault | components |



## Live Data

Live views backed by the latest collector snapshots and retained Redfish LogService journals.

### Redfish Inventory

Returns the complete current standard inventory slice selected by Redfish job, host, and resource kind. Rows include
resource identity, ownership, acquisition state, status, source provenance, readings, thresholds, and applicable
type-specific inventory fields. The Function does not filter or page rows after the required source slice is selected.


| Aspect | Description |
|:-------|:------------|
| Name | `Redfish:inventory` |
| Require Cloud | no |
| Performance | Uses the latest immutable in-memory snapshots and performs no Redfish requests. A selected source slice may contain thousands of rows; the Function returns it as one table because Netdata table Functions do not paginate. |
| Security | Exposes hardware identifiers, inventory, locations, firmware, source properties, and readings. It never exposes Redfish passwords, tokens, session locations, cookies, client keys, or proxy authorization headers. |
| Availability | Available after at least one active endpoint job publishes an inventory snapshot. |

#### Prerequisites

No additional configuration is required.

|:---------|:-----|:------------|:--------:|:--------|:--------|

| Resource Kind | select | Select exactly one standard Redfish resource kind. | yes |  |  |

| Column | Type | Unit | Visibility | Description |
|:-------|:-----|:-----|:-----------|:------------|

### Redfish Logs

## Troubleshooting

### Debug Mode

**Important**: Debug mode is not supported for data collection jobs created via the UI using the Dyncfg feature.

To troubleshoot issues with the `redfish` collector, run the `go.d.plugin` with the debug option enabled. The output
should give you clues as to why the collector isn't working.

- Navigate to the `plugins.d` directory, usually at `/usr/libexec/netdata/plugins.d/`. If that's not the case on
  your system, open `netdata.conf` and look for the `plugins` setting under `[directories]`.

  ```bash
  cd /usr/libexec/netdata/plugins.d/
  ```

- Switch to the `netdata` user.

  ```bash
  sudo -u netdata -s
  ```

- Run the `go.d.plugin` to debug the collector:

  ```bash
  ./go.d.plugin -d -m redfish
  ```

  To debug a specific job:

  ```bash
  ./go.d.plugin -d -m redfish -j jobName
  ```

### Getting Logs

If you're encountering problems with the `redfish` collector, follow these steps to retrieve logs and identify potential issues:

- **Run the command** specific to your system (systemd, non-systemd, or Docker container).
- **Examine the output** for any warnings or error messages that might indicate issues.  These messages should provide clues about the root cause of the problem.

#### System with systemd

Use the following command to view logs generated since the last Netdata service restart:

```bash
journalctl _SYSTEMD_INVOCATION_ID="$(systemctl show --value --property=InvocationID netdata)" --namespace=netdata --grep redfish
```

#### System without systemd

Locate the collector log file, typically at `/var/log/netdata/collector.log`, and use `grep` to filter for collector's name:

```bash
grep redfish /var/log/netdata/collector.log
```

**Note**: This method shows logs from all restarts. Focus on the **latest entries** for troubleshooting current issues.

#### Docker Container

If your Netdata runs in a Docker container named "netdata" (replace if different), use this command:

```bash
docker logs netdata 2>&1 | grep redfish
```

### The endpoint check fails

Verify the ServiceRoot URL, reachability, account permissions, authentication mode, proxy policy, and TLS trust.
`tls_skip_verify: true` can diagnose certificate problems but is not a secure permanent fix.


### Collection takes close to or longer than the interval

BMCs can be slow and frequently serialize work. Lower `max_concurrent_requests`, increase `timeout` only when
responses genuinely need it, increase `update_every`, or narrow `collect`.


### Detailed charts are absent but aggregates exist

The component-family population exceeded `charts.max_detailed_components_per_family`, or `charts.details` is false.
The gate is atomic: the collector never selects an arbitrary subset that would break continuity.


### Redfish logs are unavailable

Ensure the selected `redfish_logs` job exists, is enabled, and is ready. Omitted routing selects `default`.
An explicitly configured missing or disabled backend does not fall back.


### The same endpoint appears through more than one collector owner

Deterministic Redfish vnode GUIDs preserve identity but do not elect one collector. Differently named jobs and
collectors on different Agents can still poll and publish the same endpoint concurrently, which duplicates metrics
and creates a vnode identity conflict. Assign one active owner for each endpoint when using `system_vnodes`, or use
deliberate `local` placement when the endpoint data should stay on separate collector nodes.


### A standard resource is missing or incomplete

Initial compatibility evidence covers DMTF 2026.1 public schema types and embedded redundancy/leak-detection
shapes, sanitized Dell- and HPE-derived payload shapes, a modern standalone Sensor shape, and synthetic protocol
faults. Unauthenticated ServiceRoot reachability was exercised on three lab BMCs from Gigabyte and ASRock Rack;
their models and firmware were not recorded, and no authenticated resource walk was exercised. Consequently, no
vendor/model/firmware combination is claimed as live-validated, and the evidence does not prove authenticated
sessions, throttling, or full-cycle timing. No Redfish emulator was run for this qualification. Start new hardware
qualification with a Netdata nightly build, inspect partial-collection and compatibility diagnostics, and report
the affected vendor, model, firmware, and sanitized payload shape when a standard resource is missing.
