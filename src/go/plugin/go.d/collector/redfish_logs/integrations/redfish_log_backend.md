# Redfish log backend


<img src="https://netdata.cloud/img/hardware.svg" width="150"/>


Plugin: go.d.plugin
Module: redfish_logs

<img src="https://img.shields.io/badge/maintained%20by-Netdata-%2300ab44" />

## Overview

Retain Redfish LogService entries in one named local backend and monitor its readiness, storage, file, producer,
append-pipeline, retention, and synchronization metrics.


The job owns one private directory under `${NETDATA_LOG_DIR}/redfish/`, identified by a stable digest of the normalized
backend job name. It acquires an exclusive writer lock, opens the Netdata journal SDK, registers the backend route for
endpoint jobs, commits synchronized batches, and applies size-based retention to archived files.

It never polls a BMC. Redfish endpoint jobs perform LogService polling on their own `update_every` cadence and append
only while their selected backend is ready.


This collector is supported on all platforms.

This collector supports collecting metrics from multiple instances of this integration, including remote instances.

The Netdata Agent must be able to create and write its private Redfish directory below the configured log directory.

Redfish log backend can be monitored further using the following other integrations:

- [Redfish](/src/go/plugin/go.d/collector/redfish/integrations/redfish.md)

### Default Behavior

#### Auto-Detection

No backend is created automatically. The stock configuration is comment-only.

#### Limits

Each configured backend has an independent positive size-retention target of 10GB by default.

#### Performance Impact

Operational metrics refresh every second by default. Journal write cost is driven by LogEntry volume from the endpoint
jobs routed to this backend, not by the backend's `update_every`.

### Prerequisites

#### Size the retained log storage

Choose a positive `retention.max_size` for each backend. Multiple configured backends have additive disk targets.


### Configuration

#### Options

Configure one job for each desired log segment. A job named `default` receives endpoints with omitted routing.

Do not name a backend `all`, `all-local-logs`, `all-local-namespaces`, `all-local-system-logs`,
`all-local-user-logs`, `all-remote-systems`, or `all-uncategorized`. The journal query interface reserves these names
for grouped source selectors, so they cannot identify one backend uniquely.


<details open><summary>Config options</summary>



| Group | Option | Description | Default | Required |
|:------|:-----|:------------|:--------|:---------:|
| **Collection** | update_every | Operational chart refresh interval. It does not control BMC polling. | 1 | no |
|  | autodetection_retry | Failed initial-check retry interval in seconds. Zero disables retries. | 0 | no |
| **Virtual Node** | vnode | Associates backend operational metrics with an existing configured virtual node. |  | no |
| **Retention** | retention.max_size | Positive retained-size target for this backend, such as `10GB`. | 10GB | no |


</details>


#### via UI

Configure the **redfish_logs** collector from the Netdata web interface:

1. Go to **Nodes**.
2. Select the node **where you want the redfish_logs data-collection job to run** and click the :gear: (**Configure this node**). That node will run the data collection.
3. The **Collectors → Jobs** view opens by default.
4. In the Search box, type _redfish_logs_ (or scroll the list) to locate the **redfish_logs** collector.
5. Click the **+** next to the **redfish_logs** collector to add a new job.
6. Fill in the job fields, then click **Test** to verify the configuration and **Submit** to save.
    - **Test** runs the job with the provided settings and shows whether data can be collected.
    - If it fails, an error message appears with details (for example, connection refused, timeout, or command execution errors), so you can adjust and retest.


#### via File

The configuration file name for this integration is `go.d/redfish_logs.conf`.

The file format is YAML. Generally, the structure is:

```yaml
update_every: 1
autodetection_retry: 0
jobs:
  - name: some_name1
  - name: some_name2
```
You can edit the configuration file using the [`edit-config`](https://github.com/netdata/netdata/blob/master/docs/netdata-agent/configuration/README.md#edit-configuration-files) script from the
Netdata [config directory](https://github.com/netdata/netdata/blob/master/docs/netdata-agent/configuration/README.md#locate-your-config-directory).

```bash
cd /etc/netdata 2>/dev/null || cd /opt/netdata/etc/netdata
sudo ./edit-config go.d/redfish_logs.conf
```

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.

Operational state of each named Redfish retained-log backend.


### Per backend

One configured `redfish_logs` job and retained journal directory.

Labels:

| Label      | Description     |
|:-----------|:----------------|
| backend_name | Normalized backend job name. |
| backend_key | Stable digest-derived backend key. |

Metrics:

| Metric | Description | Dimensions | Unit |
|:------|:------------|:----------|:----|
| redfish.log_backend.state | Backend route readiness. | ready, unavailable | state |
| redfish.log_backend.storage | Current used bytes and configured retention target. | used, target | bytes |
| redfish.log_backend.files | Active and archived journal files. | active, archived | files |
| redfish.log_backend.producers | Endpoint jobs currently routed to this backend. | active | producers |
| redfish.log_backend.pipeline | Received, committed, duplicate-suppressed, and failed LogEntry rates. | received, committed, duplicate_suppressed, write_failed | entries/s |
| redfish.log_backend.retention_files | Archived journal files deleted by retention. | deleted | files/s |
| redfish.log_backend.retention_bytes | Archived journal bytes deleted by retention. | deleted | bytes/s |
| redfish.log_backend.sync_duration | Last append synchronization duration. | duration | seconds |



## Troubleshooting

### Debug Mode

**Important**: Debug mode is not supported for data collection jobs created via the UI using the Dyncfg feature.

To troubleshoot issues with the `redfish_logs` collector, run the `go.d.plugin` with the debug option enabled. The output
should give you clues as to why the collector isn't working.

- Navigate to the `plugins.d` directory, usually at `/usr/libexec/netdata/plugins.d/`. If that's not the case on
  your system, open `netdata.conf` and look for the `plugins` setting under `[directories]`.

  ```bash
  cd /usr/libexec/netdata/plugins.d/
  ```

- Switch to the `netdata` user.

  ```bash
  sudo -u netdata -s
  ```

- Run the `go.d.plugin` to debug the collector:

  ```bash
  ./go.d.plugin -d -m redfish_logs
  ```

  To debug a specific job:

  ```bash
  ./go.d.plugin -d -m redfish_logs -j jobName
  ```

### Getting Logs

If you're encountering problems with the `redfish_logs` collector, follow these steps to retrieve logs and identify potential issues:

- **Run the command** specific to your system (systemd, non-systemd, or Docker container).
- **Examine the output** for any warnings or error messages that might indicate issues.  These messages should provide clues about the root cause of the problem.

#### System with systemd

Use the following command to view logs generated since the last Netdata service restart:

```bash
journalctl _SYSTEMD_INVOCATION_ID="$(systemctl show --value --property=InvocationID netdata)" --namespace=netdata --grep redfish_logs
```

#### System without systemd

Locate the collector log file, typically at `/var/log/netdata/collector.log`, and use `grep` to filter for collector's name:

```bash
grep redfish_logs /var/log/netdata/collector.log
```

**Note**: This method shows logs from all restarts. Focus on the **latest entries** for troubleshooting current issues.

#### Docker Container

If your Netdata runs in a Docker container named "netdata" (replace if different), use this command:

```bash
docker logs netdata 2>&1 | grep redfish_logs
```

### Backend remains unavailable

Verify that the Netdata log directory exists and is writable, no other process owns the backend writer lock, and
the private backend identity marker matches the configured job name.


### Actual usage is temporarily above the target

`retention.max_size` is a target rather than a hard filesystem ceiling. The active file is protected from deletion
and can temporarily leave total usage above the target.
