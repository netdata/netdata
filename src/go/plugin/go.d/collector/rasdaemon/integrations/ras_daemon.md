# RAS Daemon


<img src="https://netdata.cloud/img/microchip.svg" width="150"/>


Plugin: go.d.plugin
Module: rasdaemon

<img src="https://img.shields.io/badge/maintained%20by-Netdata-%2300ab44" />

## Overview

Monitor hardware reliability errors recorded by rasdaemon, including ECC memory errors per DIMM, PCIe Advanced Error Reporting events, Machine Check Exceptions, and kernel memory failures.
Correctable ECC errors concentrating on a single memory module are an early warning of impending DIMM failure, and uncorrectable errors indicate data corruption has already occurred.


Executes `ras-mc-ctl --summary` and parses its output. rasdaemon records RAS events from the kernel tracing subsystem into a SQLite database, which persists across reboots, so the counts cover the full recorded history rather than only the current boot.
The database is installed world-readable, so no elevated privileges are required.
Memory errors are reported per physical DIMM using the motherboard's silkscreen labels (for example `DDR4_A1`) when a DIMM label database is installed for the board.


This collector is only supported on the following platforms:

- Linux

This collector only supports collecting metrics from a single instance of this integration.

None. `ras-mc-ctl` is executed unprivileged; rasdaemon's event database is installed world-readable.


### Default Behavior

#### Auto-Detection

The collector is enabled automatically when the `ras-mc-ctl` executable is found in `PATH` or in the standard system directories.


#### Limits

The default configuration for this integration does not impose any limits on data collection.

#### Performance Impact

One short-lived `ras-mc-ctl` process is spawned per collection interval (10 seconds by default).

### Prerequisites

#### Install rasdaemon

Install the `rasdaemon` package for your distribution and enable the service so that RAS events are recorded:

```bash
sudo systemctl enable --now rasdaemon
```


#### Install DIMM labels (optional but recommended)

Without a DIMM label database, memory errors are reported against anonymous EDAC identifiers rather than the physical slot names printed on the motherboard.
Most distributions register labels automatically at boot via `ras-mc-ctl --register-labels`.
If your motherboard is not yet covered, labels can be contributed upstream to rasdaemon.

#### via UI

Configure the **rasdaemon** collector from the Netdata web interface:

1. Go to **Nodes**.
2. Select the node **where you want the rasdaemon data-collection job to run** and click the :gear: (**Configure this node**). That node will run the data collection.
3. The **Collectors → Jobs** view opens by default.
4. In the Search box, type _rasdaemon_ (or scroll the list) to locate the **rasdaemon** collector.
5. Click the **+** next to the **rasdaemon** collector to add a new job.
6. Fill in the job fields, then click **Test** to verify the configuration and **Submit** to save.
    - **Test** runs the job with the provided settings and shows whether data can be collected.
    - If it fails, an error message appears with details (for example, connection refused, timeout, or command execution errors), so you can adjust and retest.


#### via File

The configuration file name for this integration is `go.d/rasdaemon.conf`.

The file format is YAML. Generally, the structure is:

```yaml
update_every: 1
autodetection_retry: 0
jobs:
  - name: some_name1
  - name: some_name2
```
You can edit the configuration file using the [`edit-config`](https://github.com/netdata/netdata/blob/master/docs/netdata-agent/configuration/README.md#edit-configuration-files) script from the
Netdata [config directory](https://github.com/netdata/netdata/blob/master/docs/netdata-agent/configuration/README.md#locate-your-config-directory).

```bash
cd /etc/netdata 2>/dev/null || cd /opt/netdata/etc/netdata
sudo ./edit-config go.d/rasdaemon.conf
```

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.

These metrics refer to the whole monitored host.

## Troubleshooting

### Debug Mode

**Important**: Debug mode is not supported for data collection jobs created via the UI using the Dyncfg feature.

To troubleshoot issues with the `rasdaemon` collector, run the `go.d.plugin` with the debug option enabled. The output
should give you clues as to why the collector isn't working.

- Navigate to the `plugins.d` directory, usually at `/usr/libexec/netdata/plugins.d/`. If that's not the case on
  your system, open `netdata.conf` and look for the `plugins` setting under `[directories]`.

  ```bash
  cd /usr/libexec/netdata/plugins.d/
  ```

- Switch to the `netdata` user.

  ```bash
  sudo -u netdata -s
  ```

- Run the `go.d.plugin` to debug the collector:

  ```bash
  ./go.d.plugin -d -m rasdaemon
  ```

  To debug a specific job:

  ```bash
  ./go.d.plugin -d -m rasdaemon -j jobName
  ```

### Getting Logs

If you're encountering problems with the `rasdaemon` collector, follow these steps to retrieve logs and identify potential issues:

- **Run the command** specific to your system (systemd, non-systemd, or Docker container).
- **Examine the output** for any warnings or error messages that might indicate issues.  These messages should provide clues about the root cause of the problem.

#### System with systemd

Use the following command to view logs generated since the last Netdata service restart:

```bash
journalctl _SYSTEMD_INVOCATION_ID="$(systemctl show --value --property=InvocationID netdata)" --namespace=netdata --grep rasdaemon
```

#### System without systemd

Locate the collector log file, typically at `/var/log/netdata/collector.log`, and use `grep` to filter for collector's name:

```bash
grep rasdaemon /var/log/netdata/collector.log
```

**Note**: This method shows logs from all restarts. Focus on the **latest entries** for troubleshooting current issues.

#### Docker Container

If your Netdata runs in a Docker container named "netdata" (replace if different), use this command:

```bash
docker logs netdata 2>&1 | grep rasdaemon
```

### No data is collected

Confirm that `ras-mc-ctl --summary` runs successfully as the `netdata` user:

```bash
sudo -u netdata ras-mc-ctl --summary
```

If it exits with an error mentioning a missing table, rasdaemon has not recorded any events yet, or was built without SQLite support. Ensure the `rasdaemon` service is running and that `/var/lib/rasdaemon/ras-mc_event.db` exists and is readable.


### Memory errors are not attributed to a DIMM slot

This means no DIMM label database is installed for your motherboard. Check with:

```bash
ras-mc-ctl --mainboard
ras-mc-ctl --print-labels
```

Labels for unsupported boards can be contributed upstream to rasdaemon.
