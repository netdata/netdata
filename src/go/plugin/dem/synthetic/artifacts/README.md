# DEM capture ownership

This store is owned by the plugin command and is separate from run history.
`Begin` creates a private run work directory; its 128-bit lowercase hexadecimal
ID is generated by the Go caller. Begin returns a short, private-data alias under
`/tmp/nd-dem-<runID>` to keep Chromium Unix socket paths below the Linux limit.
The alias points into the persistent work root; it contains no capture data.
Preexisting aliases are never adopted or replaced. Removal checks the exact
expected target. After work is handed to a child, alias removal requires the same
durable drainage evidence as work cleanup; unmarked aliases remain protected
across restart. A failed `Begin` rolls back only its own newly created resources
before a child can receive the work directory.

`Finalize` may only be called after the entire
supervised process tree has drained. Reporter completion or an old PID is not
permission to finalize or remove working files.

Finalization records and syncs a drainage marker outside the child work folder,
copies approved PNG screenshots, trace ZIPs and HTML reports from `output/`, computes size
and SHA-256, and syncs an immutable manifest before publishing the run directory.
Capture paths must be clean relative paths below `output/`, with regular files
and no symbolic-link components. Content remains potentially sensitive.

The store serializes publication, fetch, retention and close and holds a lifetime
filesystem lock. Once drainage is durably recorded, failures before publication
remove work, staging and the alias; cleanup failures retain the marker for retry.
An attempted publication whose durability is uncertain stays protected for that
owner's lifetime. A failure to persist drainage evidence also remains protected.
A later owner can remove drained work/staging leftovers; it does not reconstruct
a missing published capture. Unmarked work is never cleaned based on age or PID.
Even a temporary store is preserved on close when unverified work remains.
Same-UID or root tampering with the private store is outside the ownership model.

A nonempty publication writes a Go-authored manifest containing `job_id`, `run_id`,
`published_us`, optional `vnode_guid` and artifact membership. `Begin` snapshots the
resolved canonical vnode GUID supplied by the job at attempt admission; moving a job later does not relabel retained
captures. Older manifests without `vnode_guid` remain unassigned. No-capture finalization cleans drained work
without creating a persistent empty manifest. `Manifest` and `Fetch` require the
owning JobID; the manifest authorizes membership independently of journal history.
History is only a fallback explanation for an absent capture set, never byte access.

Manifest version 2 also retains optional artifact `test` metadata (`id`, `title`,
`text_truncated`) joined by Go from independently validated journey observations.
It cannot authorize a file or change membership. Old readers ignore these fields;
missing association means no label. Go-authored manifests and history use ordinary
typed JSON decoding; incorrectly typed stored fields make the record unreadable.
Ownership, membership, size and digest validation remain strict. Labels survive history expiry.
Capture observations and unpublished-candidate reasons live only in run history;
they do not create empty manifests or change current availability.

Retention first expires sets by publication age and rejects sets larger than the
whole allowance. It then evicts oldest non-preferred sets before the newest
eligible set per JobID; if those preferred sets do not fit, they expire oldest
first too. Publication time and RunID break ties deterministically. All logical
file lengths inside each trusted published set directory count toward the shared
retained-only allowance, including its manifest; eviction removes that whole directory.
Unclassified published entries have no trusted set identity. They, active or
unverified workspace, and pending deletions remain separate from the allowance.
No preference bypasses age or guarantees one retained set per job. Disabled jobs
keep their preference; renamed jobs form separate groups.

Eviction renames a complete set from `runs/` to `deleting/`. Both parent directories
must sync before recursive removal is authorized, including retries after restart.
The deleting parent syncs again after removal. Partial cleanup remains retryable
without depending on surviving manifest bytes. Conflicting or uncertain ownership
blocks deletion. Unknown work is never deleted through age or PID inference.

`Catalogue` reads metadata and file sizes, not payload contents. It returns sets
newest first with `(published_us, run_id)` keyset pagination; retention may remove
sets between pages. Optional job and vnode GUID filters select matching sets together;
vnode selection does not change ownership, retention preference or byte access.
Its global storage snapshot is independent of filters and
pages: effective policy, observation time, retained/workspace/unclassified/deleting
byte observations, known set/job counts, and cleanup attempt/success/error state.
Unreadable categories return unknown bytes plus an error, not a misleading zero.
A trusted set whose size cannot be measured makes retained bytes unknown and defers
retention selection until a complete inventory succeeds. Unclassified or workspace
errors do not prevent selection from a complete retained inventory.
`synthetics-artifacts` reports the last policy-reload error in its `storage` block.
A sweep is linear in stored files plus
sorting the published sets, with no rescan per eviction. Publication and current
check inventory do not recursively scan storage.

`Manifest` reads metadata without loading content. `Fetch` verifies content
against its manifest, caps returned content at 5 MiB and serializes with expiry.
Missing records return `ErrNotFound`; retained run evidence can explain these as
expired or unavailable. No tombstones grow independently of retention.
Publication skips valid candidates whose initial size exceeds the same 5 MiB limit,
after checking paths, types and PNG/ZIP signatures. Exactly 5 MiB is allowed. The retained
subset publishes atomically; no truncated artifact or empty manifest is published.
Successful finalization returns retained candidates in input order. The runner uses
candidate ID membership to record absent candidates as `too_large` without adding
a general run error.
If every candidate is omitted, drained cleanup runs and capture state is `unavailable`.

Invalid candidates and copy/close/sync errors still fail the whole publication.
Cancellation observed before publication starts also aborts it. Once the rename into
`runs/` starts, finalization finishes its durability checks even if cancellation races it.
The copy remains bounded: growth past the limit is a hard `ErrTooLarge`.
Hard size failures carry the offending candidate ID, reported as `too_large`; other
candidates in the failed set are `publication_failed`, including earlier size skips.
Fetch retains its size guard for existing oversized captures.

## Journey trace ZIPs

Trace candidates use kind `trace` and MIME `application/zip`. The store checks a ZIP local-file header (`PK\x03\x04`)
before the initial-size decision. This is a format signature check, not archive extraction or proof of every ZIP
member. The store never rewrites or sanitizes ZIP content. The existing 5 MiB limit, per-item omissions, atomic set
publication, administrator-equivalent byte access and shared retention apply.

See [Optional journey failure traces](../../README.md#optional-journey-failure-traces) for configuration, recording
cost, timeout behavior and raw-content disclosures, and the [runtime contract](../../../../../dem-runtime/README.md#optional-journey-failure-traces)
for negotiation and candidate eligibility.

Manifest version stays 2. Readers without trace support reject the entire mixed set, so its PNGs cannot be fetched
on downgrade either. These sets become unclassified and are outside age/size retention; they remain on disk and are
readable again after re-upgrade if preserved. Trace-aware readers still read older PNG/HTML sets.
