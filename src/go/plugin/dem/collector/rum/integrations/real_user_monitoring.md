# Real User Monitoring

Module: rum

<img src="https://img.shields.io/badge/maintained%20by-Netdata-%2300ab44" alt="Maintained by Netdata" />

## Overview

Measure what real visitors experience on your website (Core Web Vitals, load times, JavaScript errors and traffic),
straight from their browsers.

Add one script tag to the website, and each site job gives you:

- Web Vitals (LCP, INP, CLS, FCP and TTFB) as p50, p75 and p95, with how many experiences were good, needed
  improvement or were poor, and alerts when more than a quarter of LCP, INP or CLS experiences miss the good
  threshold.
- Document load and DOMContentLoaded times, same-site API (fetch and XHR) durations, and resource timings by host.
- Page views, application views, sessions and JavaScript errors, with errors grouped by fingerprint.
- The same measurements broken down by page, country, browser, device type and application version.
- A live feed of recent events and a history of sampled sessions, each with its timeline of pages, errors and events.
- Optionally, rage, dead and error clicks, and browser events and request traces sent to an OpenTelemetry receiver.


The website loads a small script from the Agent's [RUM Receiver](https://github.com/netdata/netdata/blob/master/src/go/plugin/dem/collector/receiver/integrations/rum_receiver.md),
which loads the [Grafana Faro](https://grafana.com/oss/faro/) Web SDK from the same receiver. The SDK reports from each
visitor's browser back to the receiver; visitors never contact a third-party service. The receiver accepts reports only
from the site's allowed origins and hands them to the site job, which keeps the last few minutes of measurements in
memory for the charts and saves the details of sampled sessions to local history on the Agent.

Before anything is charted, saved or exported, URLs lose their query strings, fragments and credentials, and path
segments that look like email addresses, IDs or tokens are replaced. Client IP addresses are used to enforce rate
limits and look up the visitor's location, and are not stored. This is not full anonymization: error messages, page
paths, user IDs that your application sets and exported event attributes can still identify people. Credentials
from the site's configuration, such as an export `auth_token`, are masked in saved and exported text when they are
at least 4 bytes long; a shorter value is masked only when it looks like a credential (`token=...` or `Bearer ...`).


This collector is only supported on the following platforms:

- Linux

This collector supports collecting metrics from multiple instances of this integration.

| Permission | Needed when |
|:--|:--|
| The Netdata service account (usually `netdata`) can read the `tls_ca`, `tls_cert` and `tls_key` files of an export destination. | Event logs or tracing send to an HTTPS receiver with a custom CA or a client certificate. |


Real User Monitoring can be monitored further using the following other integrations:

- [RUM Receiver](/src/go/plugin/dem/collector/receiver/integrations/rum_receiver.md)
- [Browser Journey](/src/go/plugin/dem/collector/synthetic/integrations/browser_journey.md)

### Default Behavior

#### Auto-Detection

This integration doesn't support auto-detection.

#### Limits

- The charts summarize the reports received in the last `window` (5 minutes by default), counted by when the receiver
  got them.
- Breakdown charts show the busiest values in that window and combine the rest as `other`: up to `page_groups` pages
  and application views and `countries` countries (20 each by default), 20 browsers, 10 application versions,
  10 error fingerprints and 10 resource hosts. The `rum-pages` Function lists every page.
- The Web Vital alerts need at least 30 observations of that vital in the window, so a quiet site never triggers them.
  No stock alert fires when traffic stops.
- Session history is shared with the synthetic monitors and kept for about 30 days, or less once it would exceed
  1 GiB (`history` in `dem.conf`). Files of up to a day expire together, so records can stay about a day longer; when the
  size limit is reached, the oldest records go first. Only sessions selected by `investigate` are saved.
- Up to 2,000 sessions per site are tracked in memory. A session that goes quiet or is pushed out loses the details
  held for it, so a later error can no longer save them.
- City locations appear only in the live feed. History and exports keep the country at most.


#### Performance Impact

The site job runs inside the DEM plugin on the Agent. Decoding reports costs CPU, and memory grows with the number of
distinct page views and sessions received recently: their measurements are kept for `window`, and the identities used
to recognize repeated reports for 30 minutes. In Netdata's tests, one site that received 450,000 page views in
29 minutes held about 630 MB of Go heap, and the DEM plugin used about two-thirds of a CPU core while it received
1,000 reports per second across 100 sites and scheduled 400 browser jobs (not counting the browsers themselves).

- `measure_sample_rate` measures a share of sessions instead of all of them, and a shorter `window` keeps less in
  memory.
- Each site has about 30 charts plus its breakdown charts. At the default limits a busy site can have about 700
  breakdown charts; lower `page_groups` and `countries` to reduce them.
- Saving sessions writes to local disk; lower `investigate.sample_rate` to save fewer.
- Event logs and tracing send data over the network to their destinations.


## Setup


### Prerequisites

#### Expose the RUM receiver to your visitors

Browsers send reports to the [RUM Receiver](https://github.com/netdata/netdata/blob/master/src/go/plugin/dem/collector/receiver/integrations/rum_receiver.md), which
listens only on `127.0.0.1:19938` by default. Put an HTTPS reverse proxy in front of it that forwards the whole `/rum/`
path, then set the receiver's `public_url` to the public address and `trusted_proxies` to the proxy's address, in
`dem/receiver.conf`. The receiver page has the details.


#### Add a site job

Add one job per website to `dem/rum.conf`, with the site key (`name`) and the origins the website is served from
(`allowed_origins`). See the examples below.


#### Add the script to your website

Once the receiver has a public URL, the `rum-sites` Function shows the script tag for each site. It looks like this,
with your receiver address and site key:

```html
<script async src="https://rum.example.org/rum/shop.js"></script>
```

- Add it to every page as a classic external script tag, with the address exactly as shown. The SDK and the reports
  use addresses relative to the tag's `src`, so a redirect of only the script does not carry over to them. A tag
  manager must insert the tag itself; pasting the script's contents inline, loading it as a module or evaluating it
  does not work.
- If the website has a Content Security Policy, allow the receiver's script address in `script-src-elem` (or
  `script-src`) and its `/rum/` address in `connect-src`. A `nonce` on the tag is passed on to the SDK scripts, and
  `strict-dynamic` works as usual. A policy that requires Trusted Types for script URLs needs your own integration:
  the script creates no permissive policy. HTTPS pages need an HTTPS receiver address.
- Optionally, set `data-version="1.4.2"` on the tag to compare application releases, call
  `window.netdataRum.setUser({ id: '...' })` to find a user's sessions later, and, once the SDK has loaded, report
  single-page application routes with `GrafanaFaroWebSdk.faro.api.setView({ name: '/checkout' })`. Use an internal,
  non-personal user ID of at most 128 bytes, and clear it when the user logs out: it is stored without hashing. It
  appears in session history only, not in the live feed, the charts or the exports.


#### Check that reports arrive

Open the website in a regular browser (automated and headless browsers are excluded by default) and look at the
browser's Network panel: the script and SDK load from the receiver, and a `POST` to `/rum/shop/collect` returns `202`.
`rum-sites` then shows a recent last accepted report for the site. Charts appear within the next `update_every`.
A `202` means the report reached the live measurements; it does not prove that it was saved or exported.


#### Optional - send event logs and traces to OpenTelemetry

Event logs (browser events, custom event attributes and optionally console messages) and browser request traces are
off by default and are exported separately, over OTLP/gRPC. The default destination, `http://127.0.0.1:4317`, is where
the Agent's [OpenTelemetry](https://github.com/netdata/netdata/blob/master/src/crates/otel-plugin/integrations/opentelemetry.md) plugin listens; there, event logs
appear in the Logs tab under the `netdata-rum` service, and spans in the Traces tab.

To follow a request from the browser into your backend, also instrument the backend services, list their origins in
`tracing.propagate_to`, allow the `traceparent` header in their CORS settings, and send their spans to the same tracing
system.

<a id="option-site-name"></a>
##### name

Browsers load the site's script from `/rum/` followed by the site key and `.js`, and send reports to `/rum/` followed
by the site key and `/collect`. After a rename, update the script tag on the website.


<a id="option-site-allowed-origins"></a>
##### allowed_origins

An origin is the scheme, host and port of the page, such as `https://shop.example.org` or `http://localhost:8080`,
without a path. Scheme and port must match exactly. `https://*.example.org` matches `https://www.example.org` and
`https://app.example.org`, but not `https://example.org`; list that separately. The `rum-sites` Function shows the last
refused origin, which helps when reports from your own pages are refused.


<a id="option-collection-window"></a>
##### window

A longer window smooths percentiles on quiet sites and gives the alerts more observations, and keeps more in memory.
Changing it restarts the measurements.


<a id="option-capture-capture-geolocation"></a>
##### capture.geolocation

City markers need a database with city data on the receiver (see the RUM Receiver page). In YAML, quote `'off'`;
unquoted, `off` is read as a boolean and the job does not start.


<a id="option-capture-capture-frustration-signals"></a>
##### capture.frustration_signals

A rage click is three clicks on one spot within a second, a dead click is a click on a link or button that changes
nothing within a second, and an error click is followed by a JavaScript error within a second. Only a short CSS
selector of the clicked element is sent, never its text. Enabling them adds click listeners to every page. They are counted on the frustration chart and, for
saved sessions, appear in the session timeline.


<a id="option-sampling-measure-sample-rate"></a>
##### measure_sample_rate

The decision is made once per browser session: a session that is not sampled sends nothing, so it cannot be saved or
investigated later. A browser session keeps its decision until it ends, even across page reloads, so a new rate
reaches a visitor in their next session. At 0 the script stops loading the SDK at the next page load, the receiver
discards reports from pages that are still open, and the measurement charts stop.


<a id="option-sampling-investigate-sample-rate"></a>
##### investigate.sample_rate

Reports that carry no session ID still count in the measurements. They are saved and exported only when
`sample_rate` is 1 or they match `always_keep`; their JavaScript errors are then saved as standalone errors,
outside any session.


<a id="option-sampling-investigate-always-keep"></a>
##### investigate.always_keep

To save details only for problem sessions, set `sample_rate` to 0 and keep the default list. When a session starts to
match, the details already held for it (up to 100 entries) are saved, and so is everything after, while the Agent
still tracks the session (up to 2,000 per site; quiet sessions expire).
Event logs and spans sent before the session matched are not exported afterwards.


<a id="option-event-logs-event-logs"></a>
##### event_logs

With the default destination, open the Logs tab of the receiving node, select the `otel-logs` source and the
`netdata-rum` service (`resource.attributes.service.name`), then filter by `resource.attributes.rum.site` (the
site key) and `attributes.session.id`. Each record's `attributes.rum.type` is `console`, `event`, `error`,
`pageview` or `vital`; look at `attributes.console.level`, `attributes.event.name`, `attributes.event.attr.KEY`,
and for errors `attributes.error.type` and `attributes.error.stack`. Viewing logs needs Netdata Cloud sign-in.


<a id="option-event-logs-event-logs-enabled"></a>
##### event_logs.enabled

Export never blocks measurements or history. On the `rum.otlp` chart, `sent` counts records the receiver accepted
(not proof that it stored them), `errors` counts records whose delivery failed or was refused (a timeout can
leave the outcome unknown), and `dropped` counts records lost locally because the queue was full or the job
stopped first. Failed records are not retried. Turning the export off keeps its saved settings without checking
them.


<a id="option-event-logs-event-logs-include-console-logs"></a>
##### event_logs.include_console_logs

Console errors are exported as logs. Uncaught exceptions and unhandled promise rejections are always collected as
JavaScript errors, with or without this option.


<a id="option-event-logs-event-logs-destination-endpoint"></a>
##### event_logs.destination.endpoint

Omit the key to use the default; an explicitly empty value is rejected while the export is on. Write IPv6
addresses in brackets, such as `https://[2001:db8::1]:4317`.


<a id="option-event-logs-event-logs-destination-auth-token"></a>
##### event_logs.destination.auth_token

A secret reference must resolve even while the export is disabled, or the job does not start.


<a id="option-browser-tracing-tracing"></a>
##### tracing

Browser spans show the browser's side of each request; they do not prove what the backend did. A session can
contain several traces, and event logs are not linked to traces automatically: look up a trace ID from the
browser in your tracing system.


<a id="option-browser-tracing-tracing-enabled"></a>
##### tracing.enabled

The `rum.spans` chart counts spans with the same `sent`, `errors` and `dropped` meaning as the event log chart
(see `event_logs.enabled`). Turning tracing off keeps its saved settings without checking them.


<a id="option-browser-tracing-tracing-destination-endpoint"></a>
##### tracing.destination.endpoint

Omit the key to use the default; an explicitly empty value is rejected while tracing is on. Write IPv6
addresses in brackets, such as `https://[2001:db8::1]:4317`.


<a id="option-browser-tracing-tracing-destination-auth-token"></a>
##### tracing.destination.auth_token

A secret reference must resolve even while the export is disabled, or the job does not start.


<a id="option-normalization-redact-paths"></a>
##### redact_paths

The built-in rules already replace path segments that look like an email address (`:email`), a UUID or a number of
six or more digits (`:id`), or a long token (`:token`). Add a rule for identifiers they miss, for example
`pattern: '/accounts/[^/]+'` with `replace: '/accounts/:account'`. These rules apply to URL paths only; they do not
change user IDs, error messages or event attributes.


<a id="option-virtual-node-vnode"></a>
##### vnode

The site's charts and alerts appear under the virtual node instead of this Agent's host, which lets you group the
real-user and synthetic monitoring of one website under one node. Define the virtual node first, as the `dem:vnode`
dynamic configuration or as a YAML file in the `vnodes/` directory of the Netdata configuration directory, then enter
its name, not its GUID. Changing it restarts the measurements; saved sessions keep the virtual node they were
recorded under.

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.

Each site has its own charts, under its virtual node when `vnode` is set and under this Agent's host otherwise.

- Percentile and count charts describe the reports received in the last `window`. Each page view counts once per Web
  Vital, with its latest value; percentiles cannot be averaged across sites or breakdown values.
- A vital with no observations in the window leaves a gap in its percentile chart; a measured zero is a real value.
- A page view is a document load or a return from the browser's back-forward cache. Single-page application route
  changes are application views, and Web Vitals stay with the page view even when reported after a route change.
- Same-site fetch timing covers the fetch and XHR requests the browser reports for the page's own site, not every
  backend request; the RUM script's own requests are excluded. JavaScript errors are events, so errors per page view
  is not a failure rate.
- Breakdown charts exist for the busiest values in the window, plus `other` for the rest (the `bucket` label).
- While the receiver is not serving, or `measure_sample_rate` is 0, the measurement charts stop; the receiver
  availability, history and export charts continue.
- The event log and span charts exist only while that export is enabled, and the frustration chart only while
  `capture.frustration_signals` is on.

## Live Data

These Functions show each site's setup and status, its recent activity, and the saved session history. They serve
every site on the Agent and are available while it has an active site or saved RUM history, so history stays readable
after a site is removed.

Viewing them requires a signed-in member of the node's Netdata Cloud Space with permission to view sensitive data, on a
paid plan or an active trial. Reports are received and history is kept on every plan.

To narrow the results to one virtual node, pass `vnode` with its configured name, or `vnode_guid` with its GUID for a
virtual node that was renamed or removed. Pass `site` for one site.

The plugin-wide `dem-history-status` Function covers the history that RUM and synthetic monitoring share. It is
available whenever the plugin runs, needs the same access and takes no parameters. It shows the retention in
effect (`history` in `dem.conf`), how much disk the history files use, and the latest cleanup, write or
configuration reload error.

## Troubleshooting

### Known Errors

#### opening DEM history: load journal identity: journalhost: machine id: no machine id found

**When**

The Agent's log shows this when `dem.plugin` starts on Linux. The plugin then exits, so no DEM job runs,
whichever modules are enabled.


**Cause**

DEM keeps its history in journal files, which need the host's machine ID, and none was found. Neither
`/etc/machine-id` nor `/var/lib/dbus/machine-id` holds a valid ID, and neither file exists under the
Netdata host prefix (`/host` in the official Docker image). This is common in minimal containers.


**Fix**

On a host, create the machine ID with `sudo systemd-machine-id-setup` (or
`sudo dbus-uuidgen --ensure=/etc/machine-id` without systemd), then restart the Agent.

In the official Docker image, mount the host's machine ID under the Netdata host prefix: add
`-v /etc/machine-id:/host/etc/machine-id:ro` to `docker run`, or the same mount under `volumes:` in Docker
Compose, then recreate the container. Check first that the host has `/etc/machine-id`: Docker creates a
missing source path as an empty directory, which DEM rejects.


#### Netdata RUM: cannot load the core SDK. Check the browser Network and CSP errors for the RUM script requests.

**Cause**

The browser console shows this when the page cannot load the SDK from the receiver: the reverse proxy does not forward the whole `/rum/` path, or the page's Content Security Policy blocks the receiver's address.

**Fix**

Check the failing request in the browser's Network panel. Forward every path under `/rum/` to the receiver, and allow the receiver's address in `script-src` and `connect-src`. If several Agents answer for the same public address, run the same Agent version on all of them, so each serves the SDK files the script refers to.

#### Netdata RUM: cannot load the tracing SDK. Check the browser Network and CSP errors for the RUM script requests.

**When**

`tracing` is enabled for the site.

**Cause**

The page could not load the tracing bundle from the receiver, for the same reasons as the core SDK. RUM keeps working without browser spans.

**Fix**

Check the failing request in the browser's Network panel. Forward every path under `/rum/` to the receiver, and allow the receiver's address in the page's Content Security Policy.

#### Netdata RUM: cannot determine receiver URL. Use the external script tag from RUM setup.

**Cause**

The script's contents were pasted into the page, or a tag manager runs them as code, instead of loading them with an external script tag.

**Fix**

Add the `<script async src=...>` tag that `rum-sites` shows. In a tag manager, insert that tag rather than its contents.

#### Netdata RUM: SDK initialization failed. Check the browser console and site script policy.

**Cause**

The SDK loaded but could not start, usually because the page's script policy (Content Security Policy or Trusted Types) blocks it.

**Fix**

Read the browser console errors logged just before this message and adjust the page's policy for the receiver's scripts.

#### The `collect` request or its `OPTIONS` request returns 403

**Cause**

The page's origin is not in `allowed_origins`. Scheme, host and port must match, and `*.example.org` does not cover `example.org` itself. A refused `OPTIONS` (preflight) request stops the browser from sending the report.

**Fix**

`rum-sites` shows the last refused origin, which can come from a preflight and stays after later reports succeed. If it is your website, add it to `allowed_origins`.

#### The `collect` request returns 400

**Cause**

The request body is not a valid RUM report. It was cut off or changed on the way, for example by a proxy, or it was not sent by the RUM script.

**Fix**

Check that the reverse proxy forwards the request body unchanged, and that the page uses the script tag `rum-sites` shows.

#### The script or `collect` request returns 404

**Cause**

The receiver has no running site job with the key in the URL: the job is disabled or failed to start, its `name` differs from the key in the script tag, or the reverse proxy changes the path.

**Fix**

Check the job's status, and that the URL path is `/rum/` followed by the site key, exactly as in the script tag from `rum-sites`.

#### The `collect` request returns 429

**Cause**

A rate limit of the receiver was reached. Behind a reverse proxy without `trusted_proxies`, every visitor appears to come from the proxy's address and shares one per-client limit (120 requests per minute by default).

**Fix**

Set `trusted_proxies` on the receiver to the proxy's address. If traffic is legitimately higher, raise `rate_limit` on the receiver.

#### The `collect` request returns 413

**Cause**

The report is larger than the receiver's `max_body_bytes` (256 KiB by default).

**Fix**

Raise `max_body_bytes` on the receiver.

#### The `collect` request returns 204 and nothing is measured

**Cause**

The request was excluded on purpose: it came from an automated or headless browser while `bots` is `exclude`, or `measure_sample_rate` is 0.

**Fix**

Test with a regular browser, or set `bots: include` to measure automated traffic as device `bot`.

#### The script loads but no `collect` request is sent

**Cause**

The browser session was not sampled (`measure_sample_rate` below 1), or the browser is automated and `bots` is `exclude`, so nothing is sent.

**Fix**

For a reliable check, set `measure_sample_rate: 1` and open the website in a new private window of a regular browser.

#### rum/otlp: site `"shop"` logs export failed: `Unavailable`

**When**

Event logs or tracing are enabled. The message is in the Agent's log, at most once a minute per site, signal and status.

**Cause**

Event logs (`logs`) or browser spans (`traces`) could not be delivered to their destination. The last word is the gRPC status: `Unavailable` means the receiver cannot be reached, `Unauthenticated` or `PermissionDenied` means the token was refused.

**Fix**

Check the destination's `endpoint`, `auth_token` and TLS settings, and that the receiver is running (for the default destination, the Agent's OpenTelemetry plugin). The `rum.otlp` and `rum.spans` charts and their alerts show delivery failures and dropped records.

#### rum/otlp: site `"shop"` logs partial rejection: `N`

**Cause**

The destination accepted the export but rejected `N` of its records.

**Fix**

Check the destination's own logs for why it rejected them.

#### allowed origin `"https://shop.example.org/home"` must be http(s)://host[:port]

**Cause**

An `allowed_origins` entry has a path, query, credentials or a scheme other than `http` or `https`.

**Fix**

Keep only the scheme, host and optional port, such as `https://shop.example.org`.

#### origin wildcard is only allowed as a leading `*.`

**Cause**

An `allowed_origins` entry uses `*` somewhere other than as the first label, such as `https://shop.*.org`.

**Fix**

Use a leading wildcard, such as `https://*.example.org`, or list the origins.

#### name must be a nonempty URL-safe site key: letters, digits, underscores or hyphens

**Cause**

The site key contains spaces, dots or other characters, or starts with an underscore or hyphen.

**Fix**

Use letters, digits, underscores and hyphens, starting with a letter or digit, such as `shop` or `shop-eu`.

#### allowed_origins is required

**Cause**

The site job lists no origins.

**Fix**

Add the origins the website is served from, such as `https://shop.example.org`.

#### page_groups and countries must be between 1 and 100

**Cause**

`page_groups` or `countries` is outside 1 to 100.

**Fix**

Use a value from 1 to 100, or remove the option to use the default of 20.

#### bots must be exclude or include

**Cause**

`bots` has another value.

**Fix**

Use `exclude` or `include`.

#### measure_sample_rate must be between 0 and 1

**Cause**

`measure_sample_rate` is negative or above 1. A percentage such as `50` is not accepted.

**Fix**

Use a share from 0 to 1, such as `0.5`.

#### redact_paths pattern `"/accounts/[^/"` is not a valid regular expression

**Cause**

A `redact_paths` pattern is not a valid regular expression in Go syntax.

**Fix**

Fix the pattern, for example `/accounts/[^/]+`. Quote it in single quotes in YAML.

#### tracing.propagate_to entry `https://api.example.org/v1` must be http(s)://host[:port] with port 1-65535

**Cause**

A `tracing.propagate_to` entry has a path, query or credentials, or is not an `http` or `https` origin.

**Fix**

List origins only, such as `https://api.example.org`.

#### capture.geolocation must be off, country or city

**Cause**

The value is not one of `off`, `country` and `city`. Unquoted `off` in YAML is read as a boolean.

**Fix**

Write `geolocation: 'off'` with quotes, or use `country` or `city`.

#### window must be between 1m and 30m

**Cause**

`window` is shorter than one minute or longer than 30 minutes.

**Fix**

Use a duration such as `5m`.

#### event_logs.destination.endpoint must be http(s)://host:port with port 1-65535

**Cause**

The event log destination has no port, has a path, or uses another scheme. The same message starts with `tracing.destination` for traces.

**Fix**

Use `http://host:port` or `https://host:port`, such as `http://127.0.0.1:4317`.

#### event_logs.destination.TLS options require an https endpoint

**Cause**

`tls_ca`, `tls_cert` or `tls_key` is set for an `http://` destination. The same message starts with `tracing.destination` for traces.

**Fix**

Use an `https://` endpoint, or remove the TLS settings.

#### event_logs.destination: invalid TLS material: could not read certificate `"/etc/netdata/ssl/otlp-ca.pem"`: open `"/etc/netdata/ssl/otlp-ca.pem"`: permission denied

**Cause**

The Netdata service account cannot read a TLS file of the destination. A client key gives `could not read key` instead, and traces give the same message starting with `tracing.destination`.

**Fix**

Check the path, and make the file readable by the Netdata service account (usually `netdata`).
