# Lighthouse Desktop Audit

<img src="https://img.shields.io/badge/maintained%20by-Netdata-%2300ab44" alt="Maintained by Netdata" />

## Overview

Audit the load performance of a web page on a schedule with Lighthouse and follow how it changes over time.

Each job loads one URL in a fresh desktop Chromium browser and gives you:

- The Lighthouse performance score, from 0 to 100.
- Lab timings: First Contentful Paint, Largest Contentful Paint, Total Blocking Time and Speed Index, plus
  Cumulative Layout Shift.
- The outcome and duration of every audit, how old the latest result is, and a run history.
- Optionally, the full Lighthouse HTML report of each audit.


Every `check_every` seconds (30 minutes by default), the Agent starts a fresh, sandboxed Chromium browser on
this host and runs a [Lighthouse](https://developer.chrome.com/docs/lighthouse/overview) performance audit of
the configured URL with the desktop preset. The browser loads the page like a visitor would, without clicking
or submitting anything.

These are lab measurements from one browser on the Agent host, so they depend on that host's network and CPU
and differ from what visitors experience. For measurements from real visitors, use Real User Monitoring. The
**Test** action in the job editor checks that the browser runtime is ready, without running an audit.


This collector is only supported on the following platforms:

- Linux

This collector supports collecting metrics from multiple instances of this integration.

The host must let an unprivileged process create the user namespaces Chromium's sandbox needs. Installing the
browser runtime prepares this on hosts that restrict it, such as Ubuntu 24.04 (see Prerequisites). Browser
jobs never run as root, and Chromium's sandbox stays enabled.


Lighthouse Desktop Audit can be monitored further using the following other integrations:

- [Browser Journey](/src/go/plugin/dem/collector/synthetic/integrations/browser_journey.md)
- [Real User Monitoring](/src/go/plugin/dem/collector/rum/integrations/real_user_monitoring.md)

### Default Behavior

#### Auto-Detection

This integration doesn't support auto-detection.

#### Limits

- All journey and Lighthouse jobs on the Agent share `browser.concurrency` in `dem.conf`, which runs one
  browser at a time by default. A check that comes due while the browser is busy waits; if it is still
  waiting when the job's next check comes due, it is skipped and counted as coalesced.
- Audits that run at the same time compete for the host's CPU, which changes their timings and scores.
- A result is fresh for two check intervals. After that the state chart shows `stale` and the duration
  and Lighthouse charts leave a gap until a new audit completes.
- Run history is shared with RUM and kept up to 30 days or 1 GiB, and reports up to 7 days or 2 GiB
  (`history` and `artifacts` in `dem.conf`). When the size limit is reached, the oldest entries go first.
- A report larger than 5 MiB is not kept.
- To be alerted on a low performance score, add your own health alert on
  `dem_synthetic.lighthouse.performance`.


#### Performance Impact

Each audit starts a new Chromium browser and Node.js process on the Agent host, which use CPU and memory for
as long as the audit lasts. The audited website receives one full page load, with all its resources.

- Raise `check_every` to audit less often. `update_every` only refreshes the charts and starts no browser.
- `browser.concurrency` in `dem.conf` limits how many browsers run at once; size it for the host's CPU and
  memory, and restart the Agent to apply it.


## Setup


### Prerequisites

#### Install the browser runtime

Journeys and Lighthouse audits run in a separately installed browser runtime (Node.js, Chromium,
Playwright and Lighthouse). Netdata never downloads it on its own, and a job waits until it is
installed. It needs Linux on amd64 or arm64.

| Netdata installation | Install the runtime with |
|:--|:--|
| Native DEB or RPM packages | The optional `netdata-dem-runtime` package, installed with your package manager. It requires a running systemd host, and stops the Agent while it installs and starts it again. |
| Static or source installation | `kickstart.sh --install-dem-runtime` during an install or update, or the installed helper: `sudo /opt/netdata/usr/libexec/netdata/netdata-dem-runtime.sh install --agent /opt/netdata/usr/sbin/netdata --allow-download` (static paths). |
| Docker (local, rootful) | `kickstart.sh --install-dem-runtime --docker-container NAME`, run on the Docker host. |

Static, source and Docker installations download the signed release named by `runtime.release_url` in
`dem.conf`, so set it to the release URL for the host's architecture first. The installation also prepares
the host so
Chromium's sandbox can run (an AppArmor allowance on Ubuntu 24.04) and test-runs a journey and a
Lighthouse audit before it is used.

The [browser runtime host setup guide](https://github.com/netdata/netdata/blob/master/packaging/installer/DEM-RUNTIME.md) covers offline installation,
Docker requirements, updates and removal.


#### Restart Netdata to activate the runtime

A running Agent keeps the runtime it found when it started. After the first installation, restart the
Agent (`sudo systemctl restart netdata`) or the container (`docker restart NAME`). The native package
does this for you. On static, source and Docker installations, runtime updates are prepared daily
(unless you installed with `--manual-updates`) and also take effect at the next restart.

To check the runtime, run as the Netdata service account:

```bash
sudo -u netdata /usr/libexec/netdata/plugins.d/dem.plugin runtime status
sudo -u netdata /usr/libexec/netdata/plugins.d/dem.plugin runtime qualify
```

`qualify` runs a test journey and a Lighthouse audit. Static installations keep the plugin under
`/opt/netdata/usr/libexec/netdata/plugins.d/`.

<a id="option-diagnosis-save-report"></a>
##### save_report

Download a report with the `synthetics-artifact` Function (administrator access) and open it in a
browser. Reports larger than 5 MiB are not kept.


<a id="option-collection-check-every"></a>
##### check_every

A new job runs its first audit right away. The second comes one to two intervals later, at a point that
depends on the job name, so jobs created together do not all run at once. After that, audits follow
every `check_every` seconds.


<a id="option-virtual-node-vnode"></a>
##### vnode

The job's charts and alerts appear under the virtual node instead of this Agent's host, which lets you
group the checks of one website under one node. Define the virtual node first, as the `dem:vnode`
dynamic configuration or as a YAML file in the `vnodes/` directory of the Netdata configuration
directory, then enter its name, not its GUID. Changing it clears the latest-result charts until the
next run; earlier runs keep the virtual node they ran under.



</details>

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.

Each job has its own charts, under its virtual node when `vnode` is set and under this Agent's host otherwise.
The charts show the latest completed run until the next one finishes. When that result is older than two check
intervals, the state chart shows `stale` and the duration, test and Lighthouse charts leave a gap instead of
repeating it.
Changing a job's `vnode` clears the latest result until the first run under the new virtual node completes.

## Live Data

These Functions show the state of every journey and Lighthouse job on the Agent, their run history and their
saved screenshots, traces and reports. They are available while the Agent has at least one active job, saved
run or saved capture, so history stays readable after a job is removed. Run history has one Function per kind;
the others serve both kinds.

Viewing them requires a signed-in member of the node's Netdata Cloud Space with permission to view sensitive
data, on a paid plan or an active trial. Jobs run and their history is kept on every plan.

To narrow the results to one virtual node, pass `vnode` with its configured name, or `vnode_guid` with its GUID
for a virtual node that was renamed or removed. Without either, every job is included, with or without a
virtual node.

## Troubleshooting

### Known Errors

#### install a browser runtime and restart dem.plugin: matching browser runtime is not prepared

**When**

Static, source or Docker installation. The job stays waiting and never runs.

**Cause**

No browser runtime is installed, or it was installed after the Agent started.

**Fix**

Install the runtime (see Prerequisites), then restart the Agent or the container.

#### install the optional netdata-dem-runtime package and restart dem.plugin: matching browser runtime is not prepared

**When**

Native DEB or RPM installation. The job stays waiting and never runs.

**Cause**

The `netdata-dem-runtime` package is not installed.

**Fix**

Install `netdata-dem-runtime` with the package manager. The package restarts the Agent when it finishes.

#### DEM browser execution requires the plugin to run as an unprivileged user; root RUM operation does not enable browser jobs

**Cause**

The Netdata service runs as root. Browser jobs refuse to start Chromium as root.

**Fix**

Run the Netdata service as its unprivileged service account (`netdata` by default). RUM keeps working either way.

#### DEM browser execution requires prepared Linux amd64 or arm64 runtime

**Cause**

The host is not Linux on amd64 or arm64, where the browser runtime is not available.

**Fix**

Run browser jobs from an Agent on an amd64 or arm64 Linux host. RUM does not need the runtime.

#### online runtime preparation requires runtime.release_url

**When**

Installing the runtime online, with kickstart, the helper or `--allow-download`.

**Cause**

`runtime.release_url` in `dem.conf` is empty.

**Fix**

Set `runtime.release_url` to the signed release URL for the host's architecture, or install offline from a downloaded release (see the [browser runtime host setup guide](https://github.com/netdata/netdata/blob/master/packaging/installer/DEM-RUNTIME.md)).

#### offline preparation requires runtime.offline_keyring; no runtime release verification key is configured

**When**

Installing the runtime from a release file and archive with `--release` and `--archive`.

**Cause**

There is no public key to verify the release signature.

**Fix**

Set `runtime.offline_keyring` in `dem.conf` to the absolute path of the Netdata release signing keyring, readable by the Netdata service account.

#### Runtime installation or qualification fails with a Chromium sandbox error

**Cause**

The host does not let an unprivileged process create the user namespaces Chromium's sandbox needs, usually because of an AppArmor restriction (Ubuntu 24.04) or a container's seccomp or namespace settings.

**Fix**

Install the runtime with kickstart or the `netdata-dem-runtime.sh` helper, which prepare the AppArmor
allowance; for Docker, use the documented container settings, including `apparmor=unconfined` on AppArmor
hosts. Look for denials in the kernel log:

```bash
sudo journalctl -k --since '10 minutes ago'
```

Do not disable Chromium's sandbox or the host's restrictions.


#### Checks are coalesced, or the state chart shows `stale`

**Cause**

The browser is busy with other jobs for longer than this job's check interval, so its checks wait and newer ones replace them. The scheduling charts show growing queue age and coalesced occurrences.

**Fix**

Raise `check_every` or lower `timeout` on busy jobs, or raise `browser.concurrency` in `dem.conf` if the host has CPU and memory to spare, then restart the Agent.

#### audit URL must be absolute HTTP(S) without credentials

**Cause**

`url` is not an absolute `http://` or `https://` URL, or it contains a username or password.

**Fix**

Use a full URL such as `https://example.org/`. Pages behind a login cannot be audited this way; check them with a journey instead.

#### Audits end as `error`

**Cause**

Lighthouse could not audit the page, for example because it did not load, the name did not resolve or the TLS certificate was not trusted.

**Fix**

Open the audit in the Lighthouse run history; its error column has Lighthouse's message. Check that the Agent host can reach the URL.
