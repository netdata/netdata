## Overview

Monitor desktop lab performance for a web page with Lighthouse. Inspect the performance category score, individual lab timings, layout shift and audit execution outcomes.

Audits the configured HTTP or HTTPS page using the Lighthouse desktop preset and sandboxed Chromium at the check_every interval. Configuration Test validates preparation without running an audit. Lab measurements describe this browser attempt and are not field Core Web Vitals.

This collector is only supported on the following platforms:

- Linux

This collector supports collecting metrics from multiple instances of this integration.

| Permission | Needed when |
|:--|:--|
| Execute the prepared Node runtime and sandboxed Chromium | Every browser attempt |
| Write to the DEM state directory | Retaining history and optional captures |


### Default Behavior

#### Auto-Detection

Jobs require explicit configuration; no websites or scripts are discovered automatically.

#### Limits

Missing scores or timings produce measurement gaps; a measured zero remains zero. Running and waiting attempts do not refresh the prior observation, which becomes stale after two check intervals. HTML reports are disabled unless requested. No stock performance-score threshold alert is configured.

#### Performance Impact

Each attempt starts a fresh browser and consumes CPU, memory and target website requests. Increasing check_every reduces browser frequency; update_every only refreshes charts. Jobs share the process browser.concurrency allowance (default 1), so concurrent due jobs can wait. Optional captures consume local disk space.

## Setup


### Prerequisites

#### Prepare the browser sandbox policy

On Ubuntu hosts with restricted user namespaces, including Ubuntu 24.04, run kickstart with
`--install-dem-runtime` for a static or source installation. The native runtime package supplies its own policy.
For local, rootful Docker on Linux, use the documented Netdata container configuration, including
`apparmor=unconfined` on AppArmor hosts. Run kickstart with `--install-dem-runtime --docker-container NAME`
on the daemon host, then run `docker restart NAME` after the first installation succeeds.
Rootless, nested and remote Docker require separate administrator setup.
Follow the [browser runtime host setup guide](https://github.com/netdata/netdata/blob/master/packaging/installer/DEM-RUNTIME.md)
for commands, offline setup and removal. Keep Chromium's sandbox enabled and qualify the actual service deployment.


#### Set up the browser runtime

Browser monitoring requires an explicitly installed runtime on Linux amd64 or arm64, running as the
unprivileged Netdata service account with Chromium sandboxing enabled. Native installations use the optional
`netdata-dem-runtime` package on live systemd hosts; package hooks may restart the Agent. Other installation
methods use managed bundles or protected preloads. Production publication still requires release and platform qualification.

For offline managed installation, set `runtime.offline_keyring` in `dem.conf` to the path of an
administrator-provisioned public OpenPGP keyring. Obtain a signed release descriptor and matching archive,
then run as the service account:

```sh
dem.plugin runtime install --release /absolute/path/release.json --archive /absolute/path/runtime.tar.zst
dem.plugin runtime status
```

Restart DEM to activate the installation. Explicit install enables automatic update preparation; add
--manual-updates for manual control. Enabling a monitor never downloads a runtime.
Use `dem.plugin runtime qualify` under the service's execution policy to check both journeys and Lighthouse.
See the [runtime setup guide](https://github.com/netdata/netdata/blob/master/src/go/plugin/dem/README.md#runtime-setup-and-retirement)
for updates, explicit downloads, installation paths and protected preloads.

## Metrics

Metrics grouped by *scope*.

The scope defines the instance that the metric belongs to. An instance is uniquely identified by a set of labels.

Charts repeat the latest completed observation until a new check finishes. Observation age and stale state retain its actual freshness; measurements older than two check intervals are omitted. Attempt and occurrence counters count each event once and reset when the native job restarts. These job diagnostics continue across vnode changes; the latest observation, age and last success/failure reset until a check for the new association completes. Coalesced occurrences never ran and do not represent website failures. Queue age tracks the oldest admission wait; scheduling delay describes the selected occurrence at the latest admission. The first check is eligible immediately, followed by a spread first interval of one to two check_every periods and then a fixed cadence. Each native job has its own chart identity. Attempt duration excludes admission waiting.

## Live Data

Use these process-wide Functions through the Agent or Cloud for both journey and Lighthouse jobs. Invoke their public synthetics-* names on the collecting Agent and select the exact configured vnode name with vnode:storefront, not its display hostname. Names use current configuration even with disabled or no jobs; renamed or removed names stop resolving, and reused names select their current GUID. Use vnode_guid for retained history by canonical GUID after removal. Omit both selectors for all vnodes and unassigned data. Filters retain Agent-level access and do not provide per-site authorization; no active browser is required. Viewing them requires a signed-in member of the node's Netdata Cloud Space with permission to view sensitive data, on a paid plan or an active trial; journeys and audits run and their history is stored on every plan.

## Troubleshooting

### Other Problems

#### No conclusive observations

Inspect native job status for unavailable dependencies and plugin logs for runtime preparation errors, waiting attempts or execution inability. Open the latest retained run for errors and actual failure phases. Missing measurements are gaps; stale, inconclusive and cancelled observations are not recovery.
