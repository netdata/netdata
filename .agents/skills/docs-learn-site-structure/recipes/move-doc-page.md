# Recipe: move a doc page

Moving changes the page's URL; the redirect from the old URL is generated by the next ingest (`../redirects.md`).

1. Confirm the page is a mapped document, not a generated integration page. Integration pages take their position
   from `metadata.yaml` through the integrations pipeline (`integrations-lifecycle`), not from `map.yaml`.
2. In `docs/.map/map.yaml`, cut the node and paste it under the new parent. Keep `edit_url` unchanged: it is the join
   key and the redirect anchor. Changing `label` at the same time is also a rename (`./rename-doc-page.md`).
3. If the source file itself moves, update `edit_url` too and accept that the catalogue's old anchor no longer resolves
   the next time the page moves (`../redirects.md#author-consequences`); prefer to leave the file where it is.
4. Run `docs/.map/validate_map_schema.py` (`../mapping.md#what-is-checked-and-by-what`) and the local ingest
   (`docs/.map/README.md#2-test-the-changes`). The new file appears under learn `docs/` at the new path, and
   `netlify.toml` and `LegacyLearnCorrelateLinksWithGHURLs.json` gain an entry for the old route.
5. Open the PR here; after merge the ingest PR carries the redirect (`../pipeline.md#when-ingest-runs`).
6. After deploy, request the old URL and confirm it redirects to the new one.

Mistakes this catches: editing `edit_url` for a pure move (the page is treated as new and the old route loses its
anchor); expecting a stale `edit_url` to fail validation (it does not; the page is silently unpublished,
`../mapping.md#the-join-key`); expecting the old URL to stop working (redirects are kept, not removed).
